## 2. Safety Post-RFC-001 — SAFE WITH 7 CONDITIONS

### No double classification risk
Line 349: `DELETE FROM marketplace_ledger_clasificado_v1` clears all rows before insert. The propagation UPDATE (line 490) is an UPDATE, not INSERT — no duplicate rows possible.

### No stale record risk
Classification reads directly from `marketplace_ledger_v1` (line 351). The full DELETE ensures no stale clasificado rows survive.

### No orphan record risk
The propagation JOIN (lines 478–489) uses `id_transaccion` and `detalle` — both exist in ledger. Every clasificado row matches a ledger row. No orphans.

### No financial corruption risk
Classification only modifies **3 columns** in ledger:
- `clasificacion_operativa` (TEXT)
- `include_in_operational_pnl` (BOOLEAN)
- `financial_group` (TEXT)

It NEVER touches: `monto`, `fecha`, `id_transaccion`, `id_orden`, or any financial amount. Zero risk to financial data integrity.

### No duplicated closing entries risk
`run_financial_closing()` (line 515) performs `DELETE FROM marketplace_cierre_financiero_v1 WHERE marketplace=? AND periodo_inicio=? AND periodo_fin=?` **before** INSERT. Completely idempotent.

### Risk: Corrections table
Lines 453–465 apply manual corrections after classification. Verified: `marketplace_correcciones_v1` contains **14 entries, all for ML** (id_transacciones with `CHG_` or `SALE_` prefix). **Zero RIPLEY corrections exist.** No stale or misaligned corrections for RIPLEY.

### Risk: normalize_detail() vs normalize()
`surgical_loader.py:normalize()` removes all non-alphanumeric chars (including spaces). `marketplace_auditor.py:normalize_detail()` preserves spaces and underscores. **This is safe** because:
- `normalize_detail()` is only used for dictionary lookup (classification mapping)
- Both sides of the propagation JOIN read from the same source (classification reads ledger, propagates back to ledger)
- The `id_transaccion` generated by `normalize()` in the loader is consistent across ledger and clasificado

## 5. Safer Recovery Strategy

Rather than executing `run_classification()` as-is (which DELETES AND RECLASSIFIES ALL marketplaces), use a RIPLEY-only approach:

**Recommended approach already implemented in `_classify_direct.py`:**
1. DELETE only RIPLEY rows from `marketplace_ledger_clasificado_v1`
2. Classify only RIPLEY rows via vectorized pandas
3. INSERT using Parquet + COPY FROM (bypasses verbose `insert_df()`)
4. SQL UPDATE ledger propagation via `(id_transaccion, detalle)` JOIN
5. Post-verification checks

**This is safer than `run_classification()` because:**
- Does NOT touch ML/PARIS/FALABELLA clasificado data (no unnecessary risk to $1.2B in correctly classified data)
- Same classification logic (same NORMALIZED_CLASSIFICATION_MAP)
- Same propagation JOIN
- Simplified execution in case of failure
